# Programmable Computer lifecycle and persistence

In a development world, use `/give @s filasignal:programmable_computer` and place the block. A new computer's bundled program prints a greeting on startup and declares no globals, so a player's first program applies without discarding saved globals. Output appears in the editor's debug panel. The first 20 lines per computer each minute are also written to the server log. The dashboard opens a native [program editor](PROGRAM-EDITOR.md). Execution remains server-side. The block's screen shows whether the program runs, stopped or failed (ADR 0018).

- **Load.** The Fabric load event queues a potential computer. The server tick admits up to 16 queued activations and 64K characters of program source, and always at least one. The block entity assigns a UUID for fresh state, decodes the saved record and compiles the program. Restore the core snapshot before queueing startup. A duplicate active ID, malformed outer record, incompatible inner snapshot or invalid program fails activation. The saved data remains available for operator intervention.
- **Execute.** One core scheduler services all dimensions of one server with a 40,000-operation tick limit. A handler receives up to 10,000 operations, 32 frames, 262,144 logical data units, eight log lines and 1,024 UTF-16 output units. The active and pending activation sets each cap at 512, shared by computers and device programs. A controller has up to 32 queued deliveries. Device host calls and event producers are described in the [device network](DEVICE-NETWORK.md).
- **Save.** Mark the chunk dirty after dispatch, including faults that leave earlier writes. During server-thread NBT capture or an unload/shutdown checkpoint, serialize the live globals into a complete core snapshot. Publish the outer record only after successful encoding. A serialization failure retains the previous complete record and reports the first failure until a save succeeds. Off-thread NBT readers see only the last published record.
- **Drives.** A drive's program, globals and named storage live in world drive records (`filasignal:drives_0` to `drives_f`), saved with the world. The device or computer block entity saves only the drive item and whether it was started there. A started device program restarts on reload with its saved globals. See [ADR 0015](../decisions/0015-autonomous-devices-and-drives.md).
- **Hardware state.** These are saved in the block's chunk NBT:
  - a Storage Server's data (at most 256 KiB, deleted with the block; undecodable data is kept unchanged and reported as damaged);
  - an Access Controller's mode, list, open time, output side and last 10 attempts;
  - a Control Panel's labels and mode;
  - a detector's event filter and an environment sensor's light threshold.

  A started device program also saves the UUID of the player who started it. Programs saved by early development builds have none and use the owner's authority. Bridge pairs are ordinary topology links in `filasignal:device_network`. Event handlers, observations and queued events are not saved: they are rebuilt when programs start again.
- **Debugger pauses.** A paused handler keeps the computer dirty, and saves keep the previous complete record until it finishes. Stop, restart, program installation, unload and shutdown cancel the paused handler first, then checkpoint the writes it made before pausing. See [ADR 0013](../decisions/0013-runtime-debugging.md).
- **Replace or unload.** Cancel pending events and detach immediately when removed, unloaded or fenced by level teardown. The load revision prevents an operator NBT replacement from being overwritten by a stale runtime. A new runtime activates on reload.
- **Stop server.** Stop accepting activations, queue shutdown deliveries and run a final dispatch under the normal tick allowance. Work still queued after that dispatch is discarded. Checkpoint and detach, then let Minecraft complete its own save. Remove the per-server runtime on the stopped event.

## Device topology

Peripheral block entities save stable UUIDs and sensor configuration in versioned chunk NBT. The Overworld SavedData record `filasignal:device_network` owns aliases, face modes and names, wireless range, endpoint locations, graph edges, ACLs and inventory bindings. Topology version 2 reads version 1 as ownerless when no ACL is present. The adjacent inventory UUID is a persistent Fabric attachment. A mismatched target leaves the grant unavailable. All endpoints begin offline when the record is decoded. Fabric load events reattach matching UUIDs at the saved position, and unload invalidates reachability while retaining known aliases. Physical removal deletes topology. Duplicate IDs at other positions are rejected. Transient redstone strengths and old sensor observations are not saved.

The codec bounds stored endpoints and edges and preserves structurally decoded records with an incompatible version or invalid graph while disabling topology. Vanilla handles unreadable compressed NBT. Back up or recover world files using the server's ordinary backups. The pinned Minecraft 26.3 `SavedDataStorage.scheduleSave` encodes dirty tags before scheduling its asynchronous write. The chunk and world data have separate save paths and can diverge after an interrupted write. There is no cross-file transaction or established crash-recovery guarantee. The Fabric test forces a flush, reads a fresh SavedDataStorage view from disk, unloads a device chunk and verifies restored reachability.

## Stored record and durability

The `filasignal_controller` NBT field carries version 1, a canonical UUID, source (at most 16,384 UTF-16 units) and an optional FilaScript snapshot (at most 262,144 bytes). Core owns checksum validation, graph serialization and schema checks. The adapter publishes one complete NBT record in memory and delegates disk writes to vanilla. In the resolved Minecraft 26.3 classes, `ChunkMap.save` captures `SerializableChunkData.copyOf` before dispatching background encoding; that capture collects block entity NBT. `RegionFile` writes payload and header separately and provides a flush operation. The verified guarantee is graceful save and reload. Power-loss atomicity and durability of the last snapshot have not been established.

The headless Fabric world test flushes vanilla saving, removes the test chunk's forced ticket, verifies unload and runtime detachment, then reloads the chunk and checks identity and the resumed startup count. This is separate from ordinary dedicated-server startup, which requires the operator's Minecraft EULA acceptance.

See [Fabric block-entity saving](https://docs.fabricmc.net/develop/blocks/block-entities) and the [core persistence contract](../engineering/PERSISTENCE.md).

## Reproduce the process restart test

1. Set `$env:FILASIGNAL_RESTART_FIXTURE='1'` in PowerShell and run `./gradlew.bat :filasignal-fabric:runGameTest --console=plain`. Read the coordinates and IDs printed by `filasignal/restart-fixture`. Clear the variable with `$env:FILASIGNAL_RESTART_FIXTURE=$null` afterward.
2. Copy `filasignal-fabric/build/run/gameTest/world` to a **new** directory `filasignal-fabric/run/m8-inventory-verified`. Run `./gradlew.bat :filasignal-fabric:runServer '--args=nogui --world m8-inventory-verified' --console=plain` with the existing local EULA setting.
3. From the console run `forceload add X Z` at the computer's coordinates, then run `filasignal status X Y Z` on each device. The fixture prints the boot counter, sensor reachability, power before writing and the barrel's ingot count. At the first dedicated activation expect `["restart-fixture",2.0,true,0.0,5.0]`.
4. Run `save-all flush`, then `stop`. Launch the same world again. The boot counter should advance, with the same device IDs, inventory grant and item count. The force-load step belongs only to this test. Runtime device discovery never requests chunk tickets.
