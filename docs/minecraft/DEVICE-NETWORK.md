# Device network

The Programmable Computer runs FilaScript and owns a network, program and persistent globals. A Network Interface relays wireless links and exposes six configurable redstone faces. A Sensor attaches through an interface and reports nearby-player transitions. A Network Repeater relays links without other functions. Dedicated hardware attaches through a relay and is described in the [hardware reference](HARDWARE.md). Device kinds compose network, relay, hardware and execution capabilities. See [ADR 0014](../decisions/0014-unified-hardware.md).

## Try it in a development world

1. Run `./gradlew.bat :filasignal-fabric:runClient --console=plain` and create a singleplayer world or join a development server. Craft a computer, two Network Interfaces, a Sensor and a Linking Tool. The recipes are listed on the public [crafting page](https://venuss1337.github.io/filasignal/minecraft/getting-started/survival/) and generated by `tools/recipes.py`.
2. Place the devices as one player. With the linking tool, right-click computer → interface, interface → interface, and interface → sensor. Sneak-right-click the second endpoint to unlink. Click the same endpoint to cancel. Selection expires after 200 ticks or disconnect.
3. Name the sensor with `/filasignal alias X Y Z entrance`. At the last interface run `/filasignal port X Y Z south output door` and place a lamp to its south. Set sensor range and polling with `/filasignal sensor X Y Z 6 10`. Inspect a device with `/filasignal status X Y Z`. Directions are fixed world faces.
4. Place barrels north of and above the final interface. At that interface run `/filasignal inventory X Y Z north storage` and `/filasignal inventory X Y Z up output`. Put iron ingots in the northern barrel. Copy [sensor-inventory.fsig](../../examples/sensor-inventory.fsig) to an unsigned Book and Quill, splitting at line boundaries if needed. Hold it and run `/filasignal install X Y Z` at the computer. `/filasignal program X Y Z SOURCE` accepts shorter inline programs. Both preserve compatible globals and validate the new code. The owner can use `program-reset` to discard a previous snapshot explicitly.
5. Leave sensor range, wait for a poll, then walk back. Confirm that the lamp lights and the output barrel receives items. Leave again and confirm the lamp turns off. Save and reopen, inspect the aliases with `status`, and repeat. Break or unlink the relay to cut the route. Replace the output barrel and verify that the alias fails until the face is approved again.

See [ownership and migration](PERMISSIONS-AND-THREADING.md). Headless tests exercised the server-side operations. A Fabric client GameTest exercised placement, linking, configuration and removal in an integrated world. A manual playthrough remains pending.

## Identity, links and addressing

- The server assigns each block a UUID. Network identity is the computer UUID. The Overworld topology record maps each UUID to a dimension, position, kind, optional alias and owning computer. Loaded entities must match their saved identity and location. Pistons cannot move the devices.
- Link a computer to a relay (an interface or repeater) first and extend from that network outward. Every link needs at least one relay endpoint. A computer or relay accepts up to 16 links, and every other device accepts one. Both endpoints must be loaded, in the same dimension and within 32 blocks of each other by default (Euclidean distance). The operator can set a world-wide range of 1–64 with `/filasignal range BLOCKS`. Lowering the range is rejected if it would invalidate a saved link. A network has up to 256 devices. The world directory holds up to 1,024 endpoints.
- Unlinking cuts the edge; members remain owned by their computer even when disconnected. Removing a peripheral removes its incident edges and aliases. Removing a computer releases its former members and clears all links in that network. Released peripherals retain their own alias and face settings. The prototype has no transfer command; old membership can also be removed by breaking and replacing a peripheral.
- Device aliases and port aliases occupy separate, case-sensitive per-network namespaces. Each is an ASCII identifier of up to 32 characters. Unloaded devices reserve their aliases. Renaming never changes UUIDs, links or another device's alias. Scripts referencing the old alias no longer resolve it. An operator may explicitly assign the vacated name again; update old scripts before reusing names.
- The graph caches reachability and invalidates it per network on topology or availability changes. Routing visits loaded endpoints only. Unload keeps identity, config and link records. No bulk world search or chunk ticket is issued by the mod. There are no cross-dimensional links.
- Two Wireless Network Bridges may be linked up to 256 blocks apart, and each bridge has at most one bridge partner. Every other rule is unchanged: same network and dimension, both loaded, owner checks. See the [hardware reference](HARDWARE.md#wireless-network-bridge).
- Device programs reach other devices through *connectivity*: loaded devices joined through loaded links, whether or not the path includes the computer. Computers reach devices through *reachability* from the computer. Both are cached per network until the topology or loaded set changes.
- Loaded devices join the topology at up to 32 per tick.

## Sampling and redstone

Polling examines at most 16 loaded endpoint slots per server tick, in rotating order. Sensors default to range 6 and period 10, configurable to ranges 1–16 and periods 5–200. Actual sampling may be slower under load. A scan uses same-dimension living, non-spectator players, with distance measured from the center of the block. Levels with more than 128 players skip sensor observations to bound the work. The sensor delivers an initial detection if occupied and then emits only first arrival and last departure. Disconnects, death and dimension changes count as departure when observed. Sensor unload, removal or loss of routing emits no synthetic clear. After reconnection or program activation the first valid observation starts from an empty baseline.

An interface face has one mode, either input or output, and one port alias. A named Redstone Controller samples its input faces the same way and raises the same events with a `name:face` argument, such as `"gate:north"`. Inputs use vanilla neighbor notifications plus bounded reconciliation polls. The server admits 96 immediate interface observations per tick before falling back to the normal rotating poll. A change emits `redstone.changed`; crossing from 0 also emits `redstone.rising`, and crossing to 0 emits `redstone.falling`. A detectable same-tick rise and fall can enqueue both edges in order. Vanilla may coalesce notifications, and the scheduler may drop observations under load. Some pulses remain unobservable. Outputs power their configured face, notify loaded neighbors, and reset to zero on unload, disconnection, removal, or reconfiguration. Output levels are transient. The affected chunk neighborhood must already be loaded before the adapter samples or drives it. Events are queued after that tick's interpreter dispatch. Queue overflow can drop observations, and no handler runs reentrantly. Game-world feedback may continue across ticks under normal budget and queue limits.

See the [implemented host calls and event payloads](HOST-API.md) and the [save lifecycle](COMPUTER-PERSISTENCE.md).
